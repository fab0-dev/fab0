# A task's pull request never skips its review gate

## Intent

Merging a stage pull request is the approval, so the person who merges needs to know whether the review gate has looked at what they merge. When an implementer returns questions, `/fab0:run` opens the task's pull request at once, before the gate runs, and nothing on that pull request says the change is unreviewed. In #5 a task was merged that way, and only the Delivered table showed it. Owners still need the questions at once, because a review can't help until they answer.

## Scope

- In: for a stage with a review gate (an agent gate), the stage pull request and its handoff comment state whether the gate has decided on the attempt the pull request holds. A pull request that holds an unreviewed attempt is a draft.
- In: questions are posted as soon as the implementer returns them. The gate doesn't run on an attempt that returned questions.
- In: when a later attempt passes the gate, the same pull request is marked ready and its statement updated.
- Out: what counts as approval. Merging stays the approval, and a person may still mark a draft ready and merge it.
- Out: stages without an agent gate (the spec stage, the deliver action, a stage with `gate: none`): their pull requests and comments are unchanged.
- Out: the Delivered table that the deliver action appends.
- Out: reviewing the work of an attempt that returned questions.
- Out: `/fab0:inbox` output.

## Scenarios

### S1: questions reach the owner at once, on a draft that says it is unreviewed

- Given a task whose implement stage has an agent gate, and whose attempt 1 returned questions
- When `/fab0:run` runs the task
- Then the gate is not handed out for attempt 1
- And the task's pull request is opened as a draft
- And its body starts with a statement that the change is unreviewed because attempt 1 returned questions
- And the questions are posted on the pull request and the item is assigned to the owner, in the same session

### S2: the handoff comment says the change is unreviewed

- Given the run of S1
- When `/fab0:run` posts the handoff comment on the run's item
- Then the comment carries the same unreviewed statement as the pull request body

### S3: a reviewed attempt makes the pull request ready

- Given the draft pull request of S1, and the owner has answered with a review on it
- When attempt 2 returns no questions and the gate decides `approve` on it
- Then the same pull request is marked ready for review
- And its body and the new handoff comment state that the gate decided `approve` on attempt 2, and no longer say it is unreviewed

### S4: a pull request opened after the gate says it was reviewed

- Given a task whose attempt 1 returned no questions and passed the gate with `approve`
- When `/fab0:run` opens the task's pull request
- Then it is not a draft
- And its body and the handoff comment state that the gate decided `approve` on attempt 1

### S5: an escalated task says what the gate decided

- Given a task whose gate escalated on attempt 3
- When `/fab0:run` opens or updates the task's pull request
- Then it is not a draft
- And its body starts with the gate's reasons, and it and the handoff comment state the gate's decision on attempt 3

### S6: a reviewed pull request goes back to draft

- Given a task whose open pull request is ready and holds an attempt the gate approved
- When a review on it leads to a new attempt that returns questions
- Then the pushed pull request is turned back into a draft
- And its body and the new handoff comment state that the change is unreviewed because that attempt returned questions

### S7: the resolver says what the gate has decided

- Given a stage with an agent gate that `fab0-resolve next` reports as waiting with reason `questions`, `human-gate` or `escalated`
- When the result is read
- Then it says whether the attempt the branch holds is reviewed, which attempt that is, the gate's decision when there is one, the sentence to state, and whether the pull request should be a draft
- And for a stage without an agent gate the result has none of this, as today

### S8: GitHub refuses the draft state

- Given the repository doesn't allow draft pull requests, or turning a pull request into a draft fails
- When `/fab0:run` handles the wait of S1 or S6
- Then the pull request is still opened or updated with the unreviewed statement at the top of its body, the questions and the handoff comment are still posted
- And the session's report says the pull request couldn't be made a draft

### S9: running the same wait twice changes nothing more

- Given `/fab0:run` already handled a wait of S1, S3 or S6
- When it is run again with no new attempt, review or input change
- Then the pull request keeps its draft state and its body, and no step fails because the state is already set

## Constraints

- The resolver stays read-only towards GitHub: it says what the pull request should be; `/fab0:run` applies it.
- Every GitHub write stays safe to repeat, and fab0 still never merges.
- Existing fields of the `wait` result keep their meaning, so `/fab0:inbox` and older sessions keep working.

## Decisions

- No gate on a questions attempt: an attempt that returned questions is incomplete by its own account, so the gate reviews the next attempt, after the answers. This is the "unreviewed, and why" path the intent allows.
- Draft as the guard: GitHub doesn't merge a draft, so an unreviewed change isn't offered for merging; the statement says why. A person can still mark it ready, which is their call.
- The resolver writes the sentence: the `wait` result of a stage with an agent gate carries a `review` object (`reviewed`, `attempt`, `decision` when reviewed, `text`) and a `draft` boolean; `/fab0:run` copies `text` verbatim into the pull request body and the handoff comment, and sets the draft state from `draft`. The wording lives in one place and tests can check it.
- The sentences: reviewed, `Reviewed: the review gate decided <decision> on attempt <n>.`; unreviewed, `Not reviewed: attempt <n> returned questions, so the review gate hasn't looked at this change. It reviews the next attempt, after the answers.`
- The body is rewritten on every update, not only when the pull request is opened, so the statement always matches the attempt the branch holds.
- Draft failure doesn't stop the run: the statement alone still meets the intent, and the questions must reach the owner.
