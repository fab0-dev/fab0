# A run shows its progress as it goes

## Intent

A run can take twenty minutes. Today the person running it sees nothing until the end. In a Docs run on 15 October, nine agent calls took 21 minutes and showed no progress at all. While a run goes on, the person needs to see what is running now: which unit, on which agent and model, which attempt, and on which branch. They need to watch the agents work, and to see how each piece ended and how long it took. Those times should stay on record, so a later report can show them as well.

## Scope

- In: a start line for each hand-out of a round, before the round runs: the unit, its agent, command or tool, the model, the attempt and the branch.
- In: each agent's activity shows in the session while it works, and the agents of a round still run in parallel.
- In: an end line when a hand-out is recorded: its outcome (verified or not, or the gate's decision) and how long it took.
- In: after each `apply`, a short list of what it did.
- In: the end report gives each unit's duration.
- In: the engine supplies these lines and times, so the session doesn't work them out. The ledger keeps each attempt's and each gate decision's start and end times, so `status` can report them later.
- In: the user docs say what a person sees during a run, on the page that describes running a pipeline. The ledger reference lists the new fields.
- Out: changing how Claude Code itself displays sub-agents.
- Out: progress in `/fab0:inbox`, on the tracker board or in pull requests.
- Out: times for actions. `apply` performs them, and they write no ledger entry (D37).
- Out: adding times to ledger entries written before this change.
- Out: the release that ships this change. It follows the run, as every release does.

## Scenarios

### S1: a start line for each agent hand-out

- Given `next` hands out `implement-T2`, attempt 2, to the agent `implementer` on `opus`, on branch `fab0/53/implement-T2`
- When `/fab0:run` starts the round
- Then before any agent starts, the session shows one line for that hand-out naming `implement-T2`, `implementer`, `opus`, attempt 2 and `fab0/53/implement-T2`. Each other hand-out of the round gets its own line too

### S2: start lines for gates, commands and tools

- Given a round hands out the reviewer gate of `implement-T1`, a command unit and a tool unit
- When `/fab0:run` starts the round
- Then the gate's line says it is the gate of `implement-T1`, with its agent (or command), model, attempt and branch. The command's line gives the command. The tool's line gives the tool's name. No line is shown for an action hand-out

### S3: the agents' activity is visible while they run in parallel

- Given a round hands out three agent units
- When the session runs them
- Then all three start together, and the session shows each agent's activity, such as the tool calls it makes, while it works, not only after all three finish

### S4: an end line when a unit is recorded

- Given `implement-T2` was handed out at 10:00:00 and its return passes every check when it is recorded at 10:04:12
- When `record` runs
- Then its result carries the start time, the end time, a duration of 252 seconds, and a line that names the unit and attempt and says it is verified and took 4m 12s. The session shows that line

### S5: the end line of a unit that fails its checks

- Given `implement-T2`'s output fails its checks, and it changed a file outside its claims in `core`
- When it is recorded
- Then its end line says it is not verified, names the failed checks (the output's name and `claims:core`), and gives the duration. The run goes on, as it does today

### S6: the end line of a gate

- Given the reviewer gate of `implement-T2`, attempt 1, was handed out and rejects the work 1 minute 5 seconds later
- When the gate is recorded
- Then its result carries the start, end and duration, and its line says it is the gate of `implement-T2`, that it rejected, and that it took 1m 5s. An approval or an escalation says that decision instead. A command gate gives the decision and the exit code

### S7: the ledger keeps the times

- Given a unit attempt or a gate decision is recorded
- When someone later reads its ledger entry, on any machine
- Then the entry holds the start and end times as UTC timestamps, and it is valid against the ledger entry schema

### S8: a refused record keeps the hand-out's start

- Given `spec` was handed out at 10:00:00, its first return doesn't match its schema, and the session calls the agent again
- When the second return is recorded at 10:07:30
- Then the refused `record` wrote no entry, and the entry that is written starts at 10:00:00 and ends at 10:07:30

### S9: a unit handed out again starts again

- Given `implement-T1` was handed out and not recorded, because the session stopped
- When a later `next` hands it out again, and it is recorded
- Then its start time is the time of the later hand-out

### S10: entries without times

- Given a run whose ledger holds entries written before this change, or a hand-out saved by an engine before this change
- When `status` runs, or such a hand-out is recorded
- Then nothing fails. The entries are still valid. A unit that has any recorded attempt or gate decision without times shows no duration, and an end line without times says the time is unknown

### S11: what `apply` did, after each `apply`

- Given `apply` merges `implement-T1` into the run branch and opens a pull request for `implement-T2`
- When `/fab0:run` runs it at the top of a round
- Then the session shows a short list with one line per thing done: the merge and the pull request, with its link. When `apply` does nothing, the session says so in one line

### S12: each unit's duration in the end report, and later

- Given `implement-T2` took 4m 12s on attempt 1, its gate took 1m 5s and rejected it, and attempt 2 took 3m 0s
- When `status` runs, at the end of the run or any time later
- Then it gives `implement-T2` a total duration of 8m 17s. The end report of `/fab0:run` shows every unit with a duration. Units never recorded show none

### S13: the session is never silent for long

- Given a real run of several rounds, with agents, gates and `apply`
- When the person watches it
- Then every hand-out shows a start line, its agent's activity while it works, and an end line with its duration. No stretch of silence is longer than one agent call

### S14: the docs say what a person sees during a run

- Given a person reads the user docs where running a pipeline is described
- When they look for what a run shows while it goes
- Then they find the start lines, the agents' activity, the end lines with outcome and duration, the list after each `apply`, and the durations in the end report. The ledger reference lists the start and end fields, and the commands reference says `status` gives each unit's duration

## Constraints

- No new runtime dependency: the standard library and the existing two.
- Additions only. No field of a hand-out, a `record` result, a `status` result or a ledger entry is renamed or removed, so existing readers keep working.
- Times are UTC with second precision. A duration is never negative: an end before its start (the clock moved) gives 0.
- Only the clock is new to the engine's output. Everything else stays deterministic.
- The session still sends a round's Agent calls together, so they run in parallel. Nothing is serialized to make it visible.

## Decisions

- Where the start comes from: `next` stamps the start time in the pending hand-out it saves (`save_pending`, `save_gate_pending`). `record` stamps the end time. Checkout time is counted in. A hand-out saved again by a later `next` gets a new start (S9).
- Ledger fields: optional `started` and `ended`, RFC 3339 UTC strings such as `2026-10-15T10:04:12Z`, on unit entries and gate entries alike. The ledger doesn't store a duration: it follows from the two times.
- `record` results, for units and gates: `started`, `ended`, `duration` (whole seconds) and `took`, plus `line`, the end line. With no start time (S10), `started`, `duration` and `took` are left out, and `line` says the time is unknown.
- Hand-outs: every hand-out except an action's gets `line`, the start line, for example `implement-T2, attempt 2: implementer on opus, branch fab0/53/implement-T2`. A gate's says `gate of implement-T2`. A command's gives the rendered command, and a tool's gives the tool's name.
- End line, for example `implement-T2, attempt 2: verified, 4m 12s`. A unit says `verified`, or `not verified` with the failed check names. It adds `exit N` for a command, and the number of questions when there are any. A gate gives its decision.
- `took` format: `42s` under a minute, `4m 12s` under an hour, else `1h 3m`. The engine has one formatting function, used by every line and by `status`.
- `status` (and `next`, which shares the unit summaries) gives each unit `duration` and `took`: the sum over all its recorded attempts and gate decisions. These are left out when any of those entries lacks times (S10), and when nothing is recorded.
- Activity in the session: `/fab0:run` makes the round's Agent calls in the foreground, all in one message, and never with `run_in_background`. Claude Code then shows each sub-agent's progress as it works. This is the intent's fix without changing Claude Code (out of scope).
- The session shows the engine's `line`s verbatim. It builds the `apply` list from `applied`, one line per entry, without interpreting it.
- Tests don't fake the clock. They check the fields' form, that `duration` matches `ended` minus `started`, and that a refused or repeated hand-out keeps or resets the start. The formatting of `took` is unit-tested directly.

## Open questions

- An engine older than this change rejects ledger entries that carry `started` and `ended`, because the ledger schema allows no other fields. — answered here: accepted. Projects follow the release with auto-update, and the release check (A.3) tells a person on an older engine to update.
