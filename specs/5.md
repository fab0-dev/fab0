# fab0-resolve reports its version

## Intent

When a run behaves unexpectedly, or two people get different results from the same run, the first thing anyone needs to know is which fab0 release produced the work. Today nothing records or reports it. People debugging a run need the resolver to say its release on request, and every piece of work it hands out to carry that release where a reviewer will see it.

## Scope

- In: `fab0-resolve --version`, which prints the release of the fab0 plugin the resolver belongs to.
- In: every stage brief and gate brief names that release in its header.
- In: the stage and gate hand-outs carry the release, and the orchestrator's commit for each stage attempt names it, so the stage pull request shows which release handed out each attempt.
- In: a check that the marketplace entry and the plugin manifest give the same release.
- Out: recording the release in ledger entries (a later Story).
- Out: any check that two people, or two attempts, use the same release.
- Out: naming the release in pull request bodies, handoff comments, `validate`, `inbox` or `record` output.
- Out: cutting a new release and moving this repo's plugin pin to it.

## Scenarios

### S1: the version on request

- Given the fab0 plugin whose manifest gives version `0.2.0`
- When someone runs `fab0-resolve --version`, from any directory, with or without a fab0 project, git repo or GitHub access
- Then it prints one JSON object `{"ok": true, "fab0_version": "0.2.0"}` and exits 0

### S2: the version can't be read

- Given a plugin whose manifest is missing, is not valid JSON, or has no non-empty string `version`
- When someone runs `fab0-resolve --version`
- Then it prints one JSON object with `"ok": false` and an `error` that names the manifest path and what is wrong, and exits 1

### S3: a stage brief names the release

- Given a run whose next step is an agent stage, with or without a task
- When `fab0-resolve next` hands it out
- Then the brief's header, right after the run line, contains the line `Handed out by fab0 0.2.0.`
- And the result has `"fab0_version": "0.2.0"`

### S4: a gate brief names the release

- Given a stage attempt recorded and waiting for its agent gate
- When `fab0-resolve next` hands out the gate
- Then the gate brief's header contains the line `Handed out by fab0 0.2.0.`
- And the result has `"fab0_version": "0.2.0"`

### S5: no brief without a release

- Given a plugin whose version can't be read, as in S2
- When `fab0-resolve next` would hand out a stage or a gate
- Then it hands out nothing: it prints `"ok": false` with the same error as S2 and exits 1, and writes no pending hand-out

### S6: the stage pull request shows the release of each attempt

- Given `/fab0:run` ran a stage attempt handed out with `fab0_version` `0.2.0`
- When it commits the attempt's work
- Then the commit subject reads `<stage>[ <task>] attempt <n> (fab0 0.2.0): <first line of the summary>`
- And so the stage pull request's commit list shows the release of every attempt in it

### S7: the two version declarations agree

- Given the marketplace entry for the `fab0` plugin and the plugin's own manifest
- When the core tests run
- Then they fail if the two versions differ, naming both

## Constraints

- `--version` must not read the project wiring, git or GitHub: it has to work where nothing else does.
- The release appears only in the header and in the `fab0_version` field. Briefs stay otherwise unchanged, so existing hand-outs and staleness checks behave as before.
- Every command still prints exactly one JSON object; exit codes keep their meaning.

## Decisions

- Source of the version: the `version` field of the plugin manifest found relative to the script (`.claude-plugin/plugin.json` under the plugin root), the same way the resolver finds its schemas. Not the project's pin, not git tags: the pin can be overridden locally and tags aren't in an installed plugin.
- `--version` prints JSON, not plain text: the resolver's rule is one JSON object per invocation.
- Field name `fab0_version` everywhere: `version` alone would read as an artifact's version in hand-out results.
- The pull request shows the release through the attempt commits, not its body: the body is written when the PR is opened, possibly by a later session on another release, while the commit is made right after the hand-out it records.
- An unreadable version is an error, not `unknown`: a brief that can't say its release defeats the point, and an installed plugin always has its manifest.
