# A run's events, readable and followable from outside its session

## Intent

While a run goes on, only the session driving it can see what it does: a person in another terminal, an unattended run's owner or another agent has to read that session's transcript. `fab0-resolve status` says where a run stands, but not what happened along the way, or when. Anyone on the machine should be able to read what a run has done, with times, and watch it as it goes on, and the inbox should say what last happened in each open run.

## Scope

- In: the engine keeps a log of each run's events, with their times: each hand-out, each recorded result, each auto gate's decision, what `apply` did, and a unit starting to wait on a person or becoming blocked by a signal.
- In: `fab0-resolve log <run>` prints that log readably, and with `--follow` keeps printing new events as they are written.
- In: `/fab0:inbox` shows the latest event of each open run.
- In: `/fab0:run` shows, once, the command that follows the run from another terminal.
- In: the user docs describe the log and the command, and say how to follow a run from outside its session.
- Out: dashboards, notifications and webhooks. The tracker stays the place for decisions (P3).
- Out: seeing a run that is driven on another machine. The log is local to the machine that runs the engine; `status`, the inbox and the tracker stay the shared view.
- Out: a person's decision on a human gate as an event of its own. It shows as what follows it: `apply`'s merge, or the reworked hand-out.
- Out: what an agent does inside a unit (its tool calls). Only the engine's events are logged.
- Out: filtering the log (by unit, by time), other output formats, and pruning or rotating logs.
- Out: events from before this change. A run already under way has events from the first command of the new engine on.
- Out: the release that ships this change. It follows the run, as every release does.

## Scenarios

### S1: hand-outs are logged

- Given run 54 whose `spec` unit is ready, and later a unit whose auto gate is due
- When `fab0-resolve next 54` hands each of them out
- Then the run's log gains one event per hand-out, with the time it was handed out (UTC, to the second), the unit, its attempt, and the hand-out's start line exactly as `next` returned it, such as `gate of implement-T1, attempt 1: reviewer on opus, branch fab0/54/implement-T1`. An action's hand-out adds no event

### S2: results and gate decisions are logged

- Given a handed-out unit, and a handed-out auto gate
- When `fab0-resolve record` records the unit, verified or not, and `record --gate` records the gate's verdict or exit code
- Then each adds one event with the time it was recorded and the end line exactly as `record` returned it, such as `spec, attempt 1: verified, 8m 28s` or `gate of implement-T1, attempt 1: rejected, 1m 5s`

### S3: a refused record adds nothing

- Given a handed-out unit whose return doesn't match its schema, or that wasn't handed out to this checkout
- When `record` refuses it
- Then the log gains no event

### S4: what `apply` did is logged

- Given a run where `apply` opens a pull request for one unit and merges another
- When `fab0-resolve apply 54` runs
- Then the log gains one event per entry of the result's `applied`, in its order, each naming the unit (or the item, or the ledger branch) and what was done. An `apply` that did nothing adds no `apply` event

### S5: a repeated `apply` report is logged once

- Given a unit whose merge waits for its pull request's required checks
- When `apply` runs three times while the checks are pending
- Then the log holds one event saying the merge waits for those checks, not three

### S6: a unit starts to wait on a person

- Given `spec` was recorded and now waits on its human gate
- When `apply` or `next` evaluates the run after that
- Then the log gains one event, such as `waiting: spec (gate human)`. Further commands while it still waits add none. A later attempt that waits again adds a new one. Questions and escalations are logged the same way, and so is the run waiting for the merge of its own pull requests

### S7: a unit becomes blocked by a signal

- Given a task blocked by an open tracker item outside the run, and other units that only wait their turn (order, data, claim, limit)
- When `apply` or `next` evaluates the run
- Then the log gains one `blocked` event for the task, with its reason, and none for the units that only wait their turn

### S8: read-only commands write no events

- Given a run with a log, and another run without one
- When `status`, `inbox`, `validate` or `log` runs, on either run
- Then neither log changes, and no log file is created

### S9: a log that can't be written

- Given the log's folder can't be written to
- When `next`, `record` or `apply` runs
- Then it does and returns what it would without the log, with the same exit code, and its result carries a warning that the run's event couldn't be logged, and why

### S10: the log reads as a list of what happened

- Given run 54 has events
- When a person runs `fab0-resolve log 54`
- Then it prints one line per event, oldest first, each the event's time and its line, such as `2026-10-16T10:12:40Z  spec, attempt 1: verified, 8m 28s`, and exits 0

### S11: a run with no events yet

- Given run 77 has no log on this machine
- When a person runs `fab0-resolve log 77`
- Then it prints one line saying run 77 has no events here yet, and exits 0

### S12: following a run as it goes on

- Given a session driving run 54, and a person who runs `fab0-resolve log 54 --follow` in a second terminal
- When the session's `next`, `record` and `apply` write events
- Then the second terminal prints the events already logged, then each new one within 2 seconds of its being written, until the person interrupts it. An interrupt (Ctrl-C) ends it with exit 0 and no traceback

### S13: following before the run starts

- Given run 78 has no log yet
- When a person runs `fab0-resolve log 78 --follow`, and a session then starts run 78
- Then it says the run has no events yet, waits, and prints the run's events as they are written

### S14: half an event is never shown

- Given the follower reads the log while an event is being written
- When it finds a last line without its end
- Then it prints nothing of it until the line is complete, and then prints it once

### S15: an unreadable event

- Given a log whose fifth line isn't a valid event
- When `log` prints it, with or without `--follow`
- Then it prints a line saying event 5 can't be read in place of that event, prints the others, and exits 0 (or goes on following)

### S16: `log` needs only the home checkout

- Given `gh` is missing or not authenticated, and the project's `.fab0/` wiring is invalid
- When a person runs `fab0-resolve log 54` from the home checkout, or with `--project <home>` from any directory
- Then it prints the log as in S10

### S17: usage errors

- Given no `.fab0/fab0.yaml` in the current directory or above it, or a run id with characters other than letters, digits, `.`, `_` and `-`
- When `fab0-resolve log` runs
- Then it prints the usual `"ok": false` object with the error, and exits 2

### S18: the inbox shows what last happened

- Given two open runs, one with events on this machine and one without
- When a person runs `/fab0:inbox`
- Then the open runs list shows, for the first, the time and line of its latest event, and the second without one. `fab0-resolve inbox` carries the latest event in its JSON for each run that has one

### S19: the session says how to follow its run

- Given a person starts `/fab0:run 54`
- When the first round begins
- Then the session shows, once, a command the person can paste into any terminal on the machine to follow the run: the engine's absolute path, `log 54 --follow` and `--project` with the home checkout's path

### S20: the docs say how to watch a run

- Given a person reads the user docs on running a pipeline and on the commands
- When they look for how to see what a run is doing from outside its session
- Then they find what the log holds and where it is kept, that it is local to the machine, `fab0-resolve log` and `--follow` with an example of its output, where `/fab0:run` shows the follow command, and that the inbox shows each run's latest event

## Constraints

- Standard library only; no new runtime dependency.
- The log stays on the machine: never committed, pushed, or written to the tracker. The ledger in git stays the record of what was delivered.
- An event holds only what the engine's lines and states already show: no brief, return data, verdict findings or tokens.
- Each event is appended as one complete line in one write, so commands running at the same time on one machine never interleave events.
- Writing an event adds no noticeable time to a command. `--follow` checks for new events about once a second and does nothing else while idle.
- The JSON results of `next`, `record`, `status` and `apply` keep every field they have today; `apply` gains `follow`, `inbox` gains each run's latest event, and only S9 adds a warning.
- Tests of `--follow` finish in a few seconds: they stop the follower themselves instead of waiting on a timeout.

## Decisions

- Where the log lives: `<home git common dir>/fab0/events/<run>.jsonl`, beside the pending hand-outs, one JSON object per line, append-only. Every checkout and worktree of the home repo, and every process on the machine, shares it; it is outside every branch, so writing it moves nothing in git.
- What an event holds: `time` (the ledger's clock: UTC, whole seconds, RFC 3339), `kind` (`handout`, `record`, `gate`, `apply`, `waiting`, `blocked`), `line`, and when they apply `unit`, `attempt` and `reason`. A core schema, `plugins/fab0/schemas/event.json`, defines it, and the engine checks each event against it before appending.
- The lines: hand-outs and records reuse the `line` the command returns, unchanged. An `apply` event reads `apply: <unit, item or ledger branch>: <what the entry says>`. A state event reads as the board's signal does (`describe` in `apply.py`): `waiting: spec (gate human)`.
- Who writes: `next` (its hand-outs, then state events after its claims), `record` (its record or gate decision, after the ledger entry is written), `apply` (its `applied` entries, then state events from its last evaluation). `status`, `inbox`, `validate` and `log` never write.
- Which states are logged: `waiting` on a person (a human gate, questions, an escalation, the run's own pull request), and `blocked` for the signals the inbox lists (`tracker`, `invalid-dependency`, `failed`, `cross-run`, `condition`, `unsupported`). A waiting that `apply` or the session settles on its own (`gate: merge`, `gate: gate`, `gate: running`) and waiting one's turn are not logged. A state event is written when a unit's state, reason and attempt differ from its last state event in the log; nothing else is stored.
- A repeated `apply` entry: one identical to the last `apply` event of the same unit isn't logged again (S5).
- `log` prints text, `<time>  <line>` per event, in UTC as kept. It is the one command whose success output isn't a JSON object; its errors are the usual JSON object and exit codes.
- `log` reads only the home checkout's git common dir: it loads no wiring, calls no tracker and makes no engine version check, so any terminal with `uv` can run it.
- `--follow` prints the whole log, then polls for appended complete lines, and never ends on its own; an interrupt ends it with exit 0.
- `follow` on `apply`'s result: the shell-quoted command `<this engine's bin/fab0-resolve, absolute> log <run> --follow --project <home main checkout>`, the engine's path found relative to its own module. `/fab0:run` shows it verbatim before the first round's `applied` list, once per run.
- A failed append becomes a `warnings` entry; it never changes the command's result or exit code.
- `inbox` adds `latest` (the last event's `time` and `line`) to each entry of `runs` that has a log on this machine, and `/fab0:inbox` shows it beside the run.
