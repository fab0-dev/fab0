# Implementers know what the other tasks of their run deliver

## Intent

An implementer sees only its own task, so it can't tell a scenario that another task delivers from a scenario nobody delivers. In run #5 the implementer of T1 asked about S6, which T2 delivered, and the question held T1 up for nothing. Implementers need to see what the rest of the run covers, so that they ask only about real gaps.

## Scope

- In: the brief of a per-task stage shows the run's other tasks; the implementer agent uses that list to decide what is a question.
- Out: how the spec author splits work into tasks; the gate (reviewer) brief and the reviewer agent; the spec stage's brief; the task issues the plan action writes; moving the home repo to a new fab0 release.

## Scenarios

### S1: the brief lists the other tasks

- Given a run whose task list has T1 (repo backend, traces to S1), T2 (repo home, traces to S1 and S2) and T3 (repo backend, traces to S3)
- When the implement stage of T2 is handed out
- Then its brief lists T1 and T3, each with its title, its repository and the scenarios it traces to, in the order of the task list
- And T2 itself is not in that list

### S2: every other task is listed, whatever its state

- Given the run of S1, where T1 is already merged and T3 is waiting on T2
- When the implement stage of T2 is handed out
- Then both T1 and T3 are listed

### S3: a task without scenarios

- Given another task of the run that traces to no scenario
- When a task's implement stage is handed out
- Then that task is listed and shown as delivering no scenarios

### S4: the only task of a run

- Given a run whose task list has one task
- When its implement stage is handed out
- Then the brief says the run has no other tasks

### S5: briefs outside the per-task step are unchanged

- Given a run at its spec stage, or at the gate of a task's implement stage
- When that stage or gate is handed out
- Then its brief has no list of other tasks

### S6: no question about another task's scenario

- Given an implementer whose task traces to S1, and a spec whose S2 another task of the run traces to
- When the implementer finishes its task
- Then it returns no question about S2

### S7: a question about a scenario no task delivers

- Given an implementer, and a spec scenario that no task of the run traces to
- When the implementer finishes its task
- Then it returns a question that names the scenario and says no task of the run delivers it

### S8: a question about work outside the task's files

- Given an implementer whose own scenario needs a change to a file its task doesn't list
- When the implementer finishes its task
- Then it leaves that file unchanged and returns a question that names the file and why the scenario needs it

## Constraints

- The resolver stays generic: the list comes from the items of the step's foreach artifact, using `id`, `title`, `repo` and `traces_to` where present, without reading the spec.
- The brief stays readable without git: the list is written into the brief, not referenced by path.

## Decisions

- Placement: a section headed `## Other tasks of this run` directly after the `## Task` section of a per-task stage brief; the agent prompt refers to it by that heading.
- Staleness: the other tasks are context, not an input. A change to another task alone doesn't make a task's finished attempt stale, so input hashes stay as they are.
- Gaps are judged by the implementer: the resolver doesn't compute which scenarios no task delivers, because it doesn't parse the spec.

## Open questions

- Should the gate brief show the other tasks too, so the reviewer doesn't list another task's scenario as unmet? — deferred to a separate issue if a run needs it (P8).
