# A person's conversation comments on a unit's pull request count as feedback

## Intent

People and agents run fab0 under one GitHub account, so on a unit's pull request a person can leave only a Comment review. People reach for a plain conversation comment first, and today it is silently ignored. A person's conversation comment should reach the unit's agent and send the unit back, exactly as a Comment review does, while fab0's own posts are not mistaken for feedback.

## Scope

- In: conversation comments on the pull requests a `pr` artifact with `part: reviews` reads (every pull request of the unit's branch). They appear in the brief alongside the reviews, oldest first. A new one makes the unit stale. Comments fab0 posts (body starting with `<!-- fab0:`) are excluded. The comments of a merged unit's pull request stop counting, as its reviews do (D61).
- In: the docs pages that describe reviews as feedback (gates, the tracker, the artifact reference, artifacts and the ledger) and the `story` example's README say so.
- Out: a separate GitHub identity for agents.
- Out: line comments on the diff that aren't part of a review's body, reactions, and comments on tracker items (the `issue` artifact's `comments` part is unchanged).
- Out: a new `pr` part or a setting to turn this off. Every factory that reads `part: reviews` gets the new behaviour.
- Out: the copies of the story example's files in this repo (`.claude/`, `.fab0/`). They follow the next example release.

## Scenarios

### S1: A conversation comment reaches the agent

- Given a step whose inputs include its unit's pull request reviews, and a person's conversation comment "Rename the flag to --dry" on the unit's open pull request
- When the unit's brief is built
- Then the reviews input shows the comment's author, labels it as a conversation comment, and includes "Rename the flag to --dry"

### S2: Reviews and comments are interleaved oldest first

- Given a Comment review at 10:00, a conversation comment at 10:05 and a Changes-requested review at 10:10 on the unit's pull request
- When the unit's brief is built
- Then the three appear in that order

### S3: A new conversation comment sends the unit back

- Given a unit whose attempt is recorded and whose pull request isn't merged
- When a person adds a conversation comment to that pull request
- Then the unit is ready for rework as stale, its brief lists `reviews` among the inputs that changed, and it includes the comment

### S4: fab0's own comments don't count

- Given a unit whose pull request carries only the comment `apply` posted for its questions or escalation (its body starts with `<!-- fab0:`)
- When the engine checks the unit and builds its brief
- Then the unit isn't sent back for that comment, and the brief says that no reviews ask for changes

### S5: A comment on a merged pull request doesn't send the unit back

- Given a unit whose pull request is merged into the branch it targets
- When a person adds a conversation comment to that merged pull request
- Then the unit isn't sent back

### S6: Comments of an earlier merged pull request stay in the brief

- Given a unit whose first pull request was merged with a conversation comment on it, and which is reworked for another reason on a new pull request
- When the new attempt's brief is built
- Then the reviews input includes that earlier comment, before the feedback on the new pull request

### S7: Recorded units without comments aren't disturbed by the upgrade

- Given a unit recorded by the previous fab0 version whose pull request has reviews but no conversation comments
- When the new engine checks it
- Then the unit isn't stale

### S8: The docs say conversation comments count

- Given the docs pages on gates, the tracker, the artifact reference, and artifacts and the ledger
- When a reader looks up how to ask for changes on a unit's pull request
- Then each page that describes reviews as feedback says a person's conversation comments count too, that fab0's own comments don't, and that they stop counting once the pull request is merged; no page still says a conversation comment is ignored

### S9: The story README tells the product owner either works

- Given the `story` example's README
- When a product owner reads how to ask for changes on the spec's pull request
- Then it says a Comment review or a conversation comment reaches the agent, and no longer says to avoid conversation comments

## Constraints

- Compatibility: when a pull request has no counted conversation comment, the `reviews` value hashes exactly as before, so upgrading doesn't send recorded units back (S7).
- One extra tracker read per pull request at most; no new permission or token scope beyond reading issue comments, which `apply` already does.

## Decisions

- Comments join the existing `reviews` part, not a new part: the story example and every factory already read it, and the intent asks for the same treatment as Comment reviews.
- A comment counts unless its body starts with `<!-- fab0:`. Its author doesn't matter: with one account, the author can't tell a person from fab0.
- In the hashed value, a review entry keeps today's shape `{state, user, body}`. A comment entry has the same keys with `state: CONVERSATION_COMMENT`, so the brief labels it "conversation comment".
- Order is by time across reviews and comments of all the branch's pull requests. The tracker gives each review its submitted time and each comment its created time. The fake tracker reads an optional `at` field, and entries without one keep their listed order.
- The merge rule (D61) needs no new code path: comments are part of the unit's own pull request input, which a merged unit already ignores.
