# An older engine stops instead of running

## Intent

After the person updates the fab0 plugin, a new Claude Code session can still put an older version's engine first on the `PATH`. A run then quietly behaves like the previous release. The person running `/fab0:run` or `/fab0:inbox` needs to know when the engine is older than the plugin installed for the project, and how to fix it, before that engine does any work. This is roadmap step A.3.

## Scope

- In: the engine compares its own release with the plugin release Claude Code has installed for the project. Every engine command that reads the project refuses to run when its release is older, and says how to fix it.
- In: `/fab0:run` and `/fab0:inbox` show that refusal and its fix, and stop.
- In: the user docs on installing the plugin say how to update it, what a person sees when the engine is older, and what they do about it.
- Out: changing how Claude Code manages its plugin cache or the `PATH`, and deleting cached versions. The engine names what to remove, and the person removes it.
- Out: re-running the command with the installed version's engine instead of stopping.
- Out: an engine newer than the installed plugin, for example one run from a development checkout. It runs as it does today.
- Out: the release that ships this change. It follows the run, as every release does.

## Scenarios

### S1: `/fab0:run` stops on an older engine

- Given the plugin installed for the project is 0.6.3, and the `fab0-resolve` on the `PATH` belongs to a cached 0.6.2
- When the person runs `/fab0:run 44`
- Then nothing is fetched, applied or handed out, and the person sees that the engine is 0.6.2 while 0.6.3 is installed, with the path of each and how to fix it

### S2: `/fab0:inbox` stops on an older engine

- Given the same session as S1
- When the person runs `/fab0:inbox`
- Then no inbox is shown, and the person sees the same message and fix as in S1

### S3: every project command refuses

- Given an engine older than the installed plugin
- When `fab0-resolve validate`, `status`, `next`, `record`, `apply` or `inbox` runs
- Then it exits 1 with `"ok": false`, an `error` naming both releases, and a `fix` list. Nothing is written: no claim, no ledger entry, no git or tracker change

### S4: the fix names the orphaned versions

- Given the installed plugin is 0.6.3, the cache also holds 0.6.1 and 0.6.2, and another project's install record uses 0.6.1
- When an engine from the cached 0.6.2 refuses
- Then the `fix` names the 0.6.2 directory to remove, doesn't name 0.6.1 or 0.6.3, and says to start a new Claude Code session afterwards

### S5: nothing to remove

- Given the engine is older than the installed plugin, and every other cached version is used by some install record
- When the engine refuses
- Then the `fix` names no directory to remove, and says to start a new Claude Code session

### S6: same or newer engine runs as before

- Given the engine's release is equal to the installed one, or newer
- When any command runs
- Then its output and exit code are what they would be without this check, with no added warning

### S7: no install record for the project

- Given Claude Code has no record of the plugin installed for this project, or no install record file at all
- When any command runs
- Then it runs as before, with no added warning

### S8: an unreadable install record

- Given the install record file isn't valid JSON, or the installed release or the engine's release isn't a dotted number such as `0.6.3`
- When `validate`, `inbox` or a run command runs
- Then it runs as before, and its result carries a warning that the engine's release couldn't be checked, and why

### S9: the record that governs the project

- Given the plugin is installed at user scope as 0.6.1, at project scope for this project as 0.6.3, and at project scope for another project as 0.7.0
- When an engine 0.6.2 runs from this project's home checkout, or from one of its unit worktrees
- Then it compares with 0.6.3 and refuses. With a local-scope record for this project as 0.6.2, it runs, because a local record takes precedence over a project one, and a project one over a user one

### S10: Claude Code's configuration directory

- Given `CLAUDE_CONFIG_DIR` points at a directory other than `~/.claude`
- When any command runs
- Then the install record and cache are read under that directory, not under `~/.claude`

### S11: `--version` is unchanged

- Given an engine older than the installed plugin
- When `fab0-resolve --version` runs
- Then it prints the engine's release and exits 0, as today

### S12: the docs say what to do after an update

- Given a person reads the user docs where installing the plugin is described
- When they look for how to update it
- Then they find the update command, that a new session is needed, the message `/fab0:run` and `/fab0:inbox` show when the engine is older, and how to fix it. The command reference lists the refusal and `CLAUDE_CONFIG_DIR`

## Constraints

- The check reads only local files: no network, no `claude` CLI call. It adds no noticeable time to a command.
- No new runtime dependency; standard library only.
- The engine never deletes or changes anything under Claude Code's configuration directory.
- Tests never read the real `~/.claude`: they point `CLAUDE_CONFIG_DIR` at a temporary directory.

## Decisions

- Where the installed release comes from: Claude Code's install record, `<config>/plugins/installed_plugins.json`, where `<config>` is `CLAUDE_CONFIG_DIR` or `~/.claude`. It is the only local source that says which version a project uses.
- Which record governs: entries keyed `<plugin name>@<marketplace>`, with the plugin name from the engine's own manifest. When the engine lives under `<config>/plugins/cache/<marketplace>/<name>/<version>/`, only that marketplace's key counts; otherwise any marketplace's. Among them, a `local` or `project` entry whose `projectPath` is the home repo's main checkout (as `find_project` resolves it), else a `user` entry. Local over project over user.
- Comparison: dotted numeric releases, compared component by component. Anything else counts as unreadable (S8), never as older.
- Where it lives: in `fab0_engine/version.py`, called from `load_wiring` in `cli.py`, so every command that reads the project checks before anything else; `--version` does not.
- How it fails: exit 1 (error), `error` naming the engine's release and path and the installed release and path, and `fix`, a list of plain sentences: each orphaned cached version directory to remove (a version directory beside the installed one that no install record uses), then "start a new Claude Code session". No new exit code.
- How the unreadable case reports: a `warnings` entry on the command's result, which `/fab0:run` already shows.
- The skills stop and show `error` and every `fix` line verbatim; they don't try another engine.
