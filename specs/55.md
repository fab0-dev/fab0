# The engine reads the tracker once per pass

## Intent

On real runs the engine's own commands take longer than the agents do: in the 21-minute Docs run of 15 October, `apply` and `next` took about 8 minutes, while the 9 agents took about 4.5. A read-only `status` of Story run 44 spends 8.7 of its 10.4 seconds on 15 tracker calls made one after another, several of them repeats. The person running a pipeline needs the engine to read each thing from the tracker once per command, make independent reads at the same time, and need one tracker pass and as few session turns as possible per round, while every command still reads the tracker's current state.

## Scope

- In: every engine command reads each thing from the tracker at most once per evaluation of the run, and makes independent reads concurrently.
- In: tracker reads that ask for related things together (the run's item with its sub-issues, relations and board fields; a pull request with its reviews and comments).
- In: board-field writes that don't read the board again for each write.
- In: one command that performs what is due and hands out what is ready, from one tracker pass; `record` without tracker reads.
- In: `/fab0:run` using that command, and recording and committing a round's hand-outs in one turn.
- In: tests that count tracker calls, so a regression shows.
- In: the docs of the changed command options and of the loop of `/fab0:run`.
- Out: keeping tracker data between commands, on disk or anywhere else. Every command reads the current state (P3).
- Out: making git calls faster, and the engine creating checkouts or committing for the session.
- Out: reads of more than 100 sub-issues, relations, reviews or comments per item; today's limits stay.
- Out: the release that ships this change. It follows the run, as every release does, and S21 and S22 are measured on it.

## Scenarios

### S1: no read is repeated in a command

- Given a Story run whose spec is merged into the run branch, with two tasks in two repositories, each task with its sub-issue of the run's item, the second blocked by the first, and each with an open pull request that has a review
- When `fab0-resolve status` runs on a fake tracker that logs its calls
- Then no read appears twice with the same arguments in the log

### S2: the sub-issue list and the run's item are read once

- Given the run of S1, whose foreach checks its sub-issues both for its `onStart` and for its `onEnd`, and whose pipeline is picked by the run item's issue type
- When `status`, `next` or `apply` runs
- Then the run's item and its sub-issues are fetched in one tracker call, made once

### S3: a run shaped like run 44 needs few calls

- Given the run of S1
- When `fab0-resolve status` runs
- Then it makes fewer than 8 tracker calls

### S4: independent reads overlap

- Given the run of S1, on a fake tracker that takes 0.3 seconds per call
- When `status` runs
- Then at least two tracker calls are in flight at the same time, and never more than 4

### S5: results don't change

- Given any run the test suite covers
- When `status`, `next`, `record`, `apply` or `inbox` runs
- Then its units, states, reasons, hand-outs, briefs and their order are what they were before this change

### S6: each command reads the current state

- Given `status` has run once on a run
- When a review is added to a unit's pull request on the tracker and `status` runs again
- Then the second `status` reads the tracker again and shows the review's effect

### S7: a round of `apply` reads again after it changed something

- Given a run where `apply` merges a unit in its first round, which makes another unit ready
- When `apply` evaluates the run again in its next round
- Then that round reads the tracker afresh, not the first round's answers

### S8: board-field writes read the board once

- Given a run with `tracker.fields.signal` set, whose item and two task items are on the board, and whose signals all change
- When `apply` runs
- Then the board and its field list are read once, and each item's field is written with one call

### S9: an item not on the board yet

- Given the run of S8, with one task item not on the board
- When `apply` sets that item's signal
- Then the item is added to the board and its field set: two writes and no extra reads

### S10: a missing field or option

- Given the board has no field named like the signal field, or a single-select field lacks the option to set
- When `apply` tries to set it
- Then it fails as today, naming the field or option and the board, and writes nothing more

### S11: a write makes no reads

- Given the GitHub adapter, with `gh` stubbed to log each call
- When it creates an issue, adds a sub-issue, adds a blocked-by relation, edits labels, assigns, comments, closes, sets a board field, opens or readies a pull request
- Then each makes only its write calls; ids it needs come from earlier reads or from the write that created the thing

### S12: `next --apply` performs, then hands out

- Given a run where something is due and a unit is ready
- When `fab0-resolve next <run> --apply` runs
- Then its result holds `applied`, as `apply` gives it, and the `handouts` and `units` that `next` run right after `apply` would give

### S13: one tracker pass for a quiet round

- Given a run where `apply` has nothing to perform and every signal is up to date
- When `next --apply` runs
- Then it makes at most one tracker call more than `status` on the same run: the one that asks who is running

### S14: `apply` fails inside `next --apply`

- Given a run whose `apply` fails, for example on a merge conflict with the base
- When `next --apply` runs
- Then it exits with `apply`'s code and error, and hands out and claims nothing

### S15: `--unit` with `next --apply`

- Given a run with two ready units, T1 and T2, and something due for T2
- When `next <run> --apply --unit T1` runs
- Then `apply` performs what is due for every unit, T2's included, and only T1 is handed out. When T1 isn't ready, it is refused with exit 4, and the result still lists what `apply` did

### S16: a finished run

- Given a run that is `done`, or `waiting` for the merge of its pull request
- When `next --apply` runs
- Then it hands out nothing, and its `kind` is `done` or `waiting`

### S17: `record` doesn't read the tracker

- Given a project with one pipeline and a unit handed out
- When `fab0-resolve record` records it, verified or not
- Then it makes no tracker call, and its ledger entry and result are what they were before this change

### S18: `record` with several pipelines

- Given a project with two issue-triggered pipelines, and `record` called without `--pipeline`
- When it records a unit
- Then its only tracker call reads the run's item, to pick the pipeline

### S19: a round of `/fab0:run` in four turns

- Given a round that hands out three agents
- When `/fab0:run` runs it
- Then the session uses one turn for `next --apply`, one for the checkouts, one for the agents and one to record and commit all three; and it still shows what `apply` did, every start line and every end line, as before

### S20: a refused record in a combined turn

- Given a round of three hand-outs, one of whose returns doesn't match its schema
- When the session records and commits them
- Then the other two are recorded and committed, the refused one is not committed, and the session calls its agent once more with the errors, as before

### S21: run 44, measured

- Given the release with this change, and a logging `gh` wrapper
- When `fab0-resolve status 44` runs
- Then it makes fewer than 8 tracker calls and finishes in under 4 seconds

### S22: a real run, measured

- Given the release with this change
- When a real Story or Docs run goes through `/fab0:run`
- Then the engine's per-round commands (`next --apply`) take less than half the time per round that `apply` and `next` together took in the Docs run of 15 October

### S23: the docs say how a round goes

- Given a person reads the commands reference and the page on running a pipeline
- When they look up `next` and the loop of `/fab0:run`
- Then they find `--apply` and what it returns, that `--unit` limits only the hand-outs, and the loop as `/fab0:run` now follows it

## Constraints

- No new runtime dependency: concurrency uses Python's standard library (D6). GitHub is reached only through `gh`, as today.
- At most 4 tracker calls in flight at once, to stay clear of GitHub's secondary rate limits.
- Nothing read from the tracker outlives the command that read it (P3).
- `next` and `apply` without the new option behave as today, so a session that runs them separately still works.
- The engine still never reads the signal field back to decide anything (D51); reading it to skip an unchanged write stays as today.

## Decisions

- Reads are memoized for one evaluation of the run: a whole `status`, `next` or `inbox`, and one round of `apply`. Writes don't update the memo; `apply`'s next round starts with nothing memoized. The memo, the GitHub adapter and the fake are safe to call from several threads, so the evaluation can run its reads concurrently without further locking.
- The run's item is read in one GraphQL query: its type, labels, state, assignees, board fields and board entry, its blocked-by items, and its sub-issues with the same facts and their own blocked-by items. Reads of the issue, sub-issues, blocked-by and board fields of those items are answered from it. Other items are read on their own.
- A pull request is read, per repository, head and base, in one query with its reviews and conversation comments. Its diff and its required checks are separate reads, made only where they are needed today.
- The board's id, its fields and their options are one read, made at most once per command.
- Every adapter write makes only write calls: the ids it needs come from reads or from the write that created the thing. Adding an item to the board and setting its field are two writes.
- Independent reads run on a thread pool of at most 4. Prefetched reads are only those the evaluation then uses, and the order of everything in the output is the sequential order.
- The fake tracker logs every call to `<FAB0_GH_FAKE file>.calls`, one JSON line each with the method, its arguments, and its start and end times, and waits `delay` seconds per call when the fake file has that key. One fake call stands for one request to GitHub, so the tests count what GitHub would see.
- The combined command is `fab0-resolve next <run> --apply`. It runs `apply` for every unit, then hands out from `apply`'s last evaluation. `--unit` limits only the hand-outs, as `/fab0:run` passes it to `next` only today.
- `record` reads nothing from the tracker beyond what picking the pipeline needs: after the pick, it evaluates the run against a tracker that answers every read with nothing. The unit and its context come from git and its saved hand-out, as its entry already does.
- The session still makes the commits. Each hand-out's `record` and its commit run in one Bash call, chained so a refused record commits nothing; a round's calls go in one message.
